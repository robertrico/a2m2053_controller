# M9: robustness

Started 2026-10-15. Goal (parent spec sec. 4.2): disk swap mid-session,
write-protected disk, empty drive, long copy loops.

Pass rule: behave like the working UniDisk and recover without a power
cycle. Abuse cases (eject mid-transfer, reset mid-transfer) don't have to
succeed; the original fails them too. They must not wedge the board or
hand the next disk stale data.

Rig as at the end of M8: our board in front (S5,D1), the working UniDisk
behind it (S5,D2), Pico on IIe +5 through the diode, 24 AWG on +5.

## Results (2026-10-15)

| Test | Result |
|---|---|
| Swap disks at the prompt, read, catalog | OK, many swaps |
| Swap, then copy one file onto the new disk | OK. SDMTEST4 copied onto `/REF800K`; catalog shows it with the other files intact, 87 free + 1513 used = 1600 |
| Format a write-protected disk (Copy II Plus) | Refused, "DISK IS WRITE-PROTECTED" |
| Copy a file to a write-protected disk | Refused |
| Empty drive | `$2F` on reads, STATUS `$E8` (SPCOMPARE, M8 clean-boot check) |
| Eject mid-transfer | Both drives (ours and the UniDisk) allow the eject, then the Apple gets an error. Same behavior. The next disk works with no reboot |
| Format on the UniDisk through our pass-through, then ADTPro writes to D1 | OK, no hangs or glitches |
| ADTPro disk writes to D1, repeated | OK, no errors |
| Pico power cycles, soft and hard resets | Board comes back and serves as before |
| Board counters after the ADTPro run (since the last power-on) | 1 FORMAT, 1610 WRITEBLOCKs, 637 READBLOCKs, 853 packets passed to the UniDisk; 0 timeouts, 0 re-reads, 0 checksum errors, 0 late ACKs; longest command 884 ms |

Counters: `docs/captures/m9/2026-10-15_console.log`. Screens in `docs/captures/m9/`:

Why swap-then-write is the swap test that matters: the board keeps a
whole track in RAM. Writing a file is read-modify-write on the volume
bitmap and directory. If those reads came from the old disk's buffered
track, ProDOS would write the old disk's bitmap and directory onto the
new one. The buffer is cleared on every eject, on no-disk and on a failed
read; the SDMTEST4 copy shows it held.

## Decisions

- No 3V3 supervisor on the PCB. The M0 LSTRB strobe at power edges can at
  worst make the mechanism step or blip at power-on, which the stock UniDisk
  and DuoDisk do anyway. No disk spins and nothing is written at that
  moment, and the power cycles above showed nothing odd. No scope capture
  needed.

## Prototype checks (FABRICATION.md)

- In-use LED: blinks with drive activity, so the J5 polarity guess is right.
  Blink timing can be tuned in firmware later.
- Pico on the diode: boots from the IIe alone; the diode was tested live
  against USB back-feed in M8.
- Eject button (bench switch on GP22): works throughout M9.
- Write speed: an ADTPro write to D1 feels no different from one to the
  UniDisk. The verify on the next revolution stays.

## M9 result

Passed on the bench. Swaps, writes after a swap, write-protected and empty
drives, eject and resets mid-transfer all behave like the UniDisk, and the
board never needed a power cycle to recover. 1610 writes in one session
with no errors.
