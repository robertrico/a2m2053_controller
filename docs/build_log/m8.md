# M8: daisy chain

Started 2026-10-13. Goal (parent spec sec. 4.2): our board in front of the
working UniDisk, then behind it. INIT assigns both, ProDOS sees both drives,
/ENBL pass-through rule confirmed. Merged to main 2026-10-15 (`a1e51db`).

Bench names in this note: **J1** = host IDC20 (from the IIe), **J2** =
mechanism (CN104), **J3** = rear IDC20 (to the next drive). The KiCad
schematic names the host connector J3 and the rear DB-19 J1.

## Rear port: what the original does (2026-10-13)

Beeped on a dead IF-83, CN101 (rear DB-19) against CN102 (host IDC20). Same
map as the 2026-10-07 test (`research_notes.md` sec. 10). **[measured]**

- 16 of 19 rear pins are straight copper to CN102: GND (1-4), -12 V (5),
  +5 V (6), +12 V (7, 8), HDSEL (9), ACK (10), PH0-2 (11-13), /WRREQ (15),
  RD (18), WR (19).
- Three go to the CXD1013 instead: 14 (PH3 out, pin 4), 16 (LASTONE/, via a
  1k to pin 5), 17 (/ENBL out, pins 12 and 13).
- CN102.12 (DB-19 pin 16 on the host side) beeps to GND.

So the chain presence signal is passive: every drive grounds pin 16 on its
input port, and senses pin 16 on its output port through a 2k pull-up. Low
means a drive is behind it; high means it is last. A drive never reads its
own grounded pin.

Our board needs three GPIO for the chain (PH3_OUT, ENBL_OUT, LASTONE/), as
planned in `pin_budget.md`. Everything else is copper from J1 to J3.

## What was built

- **J3**: IDC40 breakout, positions 1-20 used. 20-wire ribbon crimped flat
  at the IDC40 end (wire n = J3.n), DB-19 female soldered wire by wire at
  the other end in Apple's internal mapping, same as J1: wire 2n-1 -> DB n
  (n = 1-9), wire 2k -> DB 10+k (k = 1-9), wire 20 -> DB 10 (ACK), wire 19
  cut. Every DB pin heat-shrunk. Full map: `pin_budget.md` "J3".
- **J1 -> J3 copper**: J1.n -> J3.n for 1-7, 9-11, 13, 15-18 and 20. The
  rails (9, 11, 13, 15) run J1 -> J3 only, not onto the bench nets.
- **J1.12 -> GND**, so a drive in front of us sees us.
- **U4** (A->B, DIR = 3V3, /OE = GP21 shared with U2): A1 = GP0 -> B1 =
  J3.8 PH3_OUT (10k to GND); A2 = GP27 -> B2 = J3.14 ENBL_OUT (10k to
  +5 V); A3 = GP26 -> B3 = LED (R17 330). A4-A8 to GND.
- **U5** (B->A, DIR = GND, /OE = GND): B1 = J3.12 LASTONE/ (2k to +5 V) ->
  A1 = GP1. B2-B8 to GND.

Channel assignments follow the KiCad schematic, so the bench matches the PCB.

## Firmware: `loop` (`31e3e0a`)

A console command for the loopback. With `server off` and `sp off` it turns
on U2/U4 (mechanism /ENBL stays high) and U3, then drives PH3_OUT, ENBL_OUT,
host RD and ACK one at a time through a fixed 32-step pattern (50 us per
step). For each driver it prints which inputs followed (or inverted) it and
any input that moved out of step (`mixed`). Inputs: LASTONE/, PH0-3,
/WRREQ, /HSTEN, WR, mechanism RD. The host RD pad goes from the PIO to plain
GPIO for the test and back afterwards. U3 drives J1 meanwhile, so the host
cable must be off the Liron card.

## Cable loopback (2026-10-15)

Rear DB-19 plugged into the host DB-19 cable, host cable off the Liron,
mechanism connected, IIe off. Log: `docs/captures/m8/2026-10-15_console.log`.

Flashing first failed four times with `Error connecting DP: cannot read IDR`
(probe found, target silent, SWCLK and SWDIO both read 0). Replugging the
Pico USB and the Debug Probe USB fixed it.

| Run | Condition | Result |
|---|---|---|
| 1 | bench +5 off | every driver `none`; inputs float (only GP1, with its internal pull-up, read 1) |
| 2 | bench +5 on | idle sane (/WRREQ = 1, /HSTEN = 1, mech RD = 1); GP0 -> GP5 PH3 follows; GP27 -> GP7 /HSTEN follows; RD, ACK none; LASTONE/ = 1 |
| 3 | J1.12 -> GND fitted | as run 2, and LASTONE/ = 0 |

What that proves:

- PH3_OUT: GP0 -> U4 -> J3.8 -> rear DB 14 -> host DB 14 -> J1.8 -> U1 ->
  GP5.
- ENBL_OUT: GP27 -> U4 -> J3.14 -> rear DB 17 -> host DB 17 -> J1.14 -> U1
  -> GP7.
- LASTONE/: J1.12 GND -> host DB 16 -> rear DB 16 -> J3.12 -> U5 -> GP1. An
  open U5 path would read 1 (pull-ups).
- No line moved with the wrong driver; `mixed=0` in every run.

RD and ACK show `none` as expected: in a cable loop each pass-through line
only meets itself, and no input sits on RD or ACK.

## Pass-through: end-to-end beep (2026-10-15)

The pass-through lines are plain copper, so continuity proves them; a
jumper test would only add contacts. Host DB-19 plug against rear DB-19
socket, loopback unplugged. All as expected: **[measured]**

- Pins 1-13, 15, 18, 19 beep host to rear (both cables, both breakouts and
  the J1 -> J3 wires in one test).
- 14, 16, 17 open host to rear (the gated lines).
- Host 16 beeps to GND; rear 16 does not.
- Rails (5, 6, 7, 8) do not beep to any signal pin or to the bench +5/+12
  nets. 7 and 8 beep to each other (both +12 V).

The rear port is wired and proven. HDSEL has no Pico pin, so the beep is
its only check.

## Chain firmware (2026-10-15)

Parent spec sec. 3.5, following the ROM's gate-array use (`liron.asm`:
PH3EN set with `$44` once every internal drive has an ID, cleared only by
reset):

- Bus reset: ID cleared, rear port off (PH3_OUT low, ENBL_OUT high, plain
  GPIO).
- First INIT while we have no ID: take the ID, read LASTONE/ (high = last,
  INIT status `$40`), then turn the pass-through on before our reply goes
  out.
- Pass-through: one PIO instruction (`mov pins, pins`, `sp_chain.pio`) on
  two state machines in PIO2 (PIO0 is full, PIO1 has the flux side):
  host PH3 (GP5) -> PH3_OUT (GP0), host /ENBL (GP7) -> ENBL_OUT (GP27).
- INIT once we have an ID is for a drive behind us: no ACK.
- `loop` parks the pass-through while it runs and restores it after.

Host test (`test_sp_bus.c` case 14): LASTONE/ low, INIT 1 answered with
`$00`, pass-through on before the reply, INIT 2 not ACKed, a READBLOCK for
ID 2 followed by REQ held high gets no re-send from us, bus reset turns the
pass-through off.

## UniDisk behind our board (2026-10-15)

Working UniDisk on J3, our board on the Liron. `sp` after boot: LASTONE=0,
`id=1 last=0 pass=1`, INIT for ID 2 ignored by us and taken by the UniDisk.

### Bug: our stale reply on top of the UniDisk's

Bitsy Bye skipped S5,D2. `splog` showed `IGN d=2 c=01 b=2` then `REREAD`:
after a command for ID 2 the card raises REQ to read the UniDisk's reply,
and our re-read detector (REQ high, no write, an old reply still valid)
sent our last reply again over the UniDisk's. With one drive that detector
is right; in a chain it is not. Fix: a command packet that is not ours
(ignored, or a checksum error) clears the saved reply. Test first (fails
before the fix), then the fix.

### Slow: the UniDisk was short of +5

After the fix S5,D2 listed, but only after a long wait: the card re-sent
READBLOCK 2 to ID 2 about 6000 times in a row. The UniDisk's light stayed on
and its motor spun from boot, and its eject button did nothing.

- Order swapped (UniDisk on the Liron, our board behind it): both quick. We
  took ID 2 with LASTONE=1 (`id=2 last=1`), as designed.
- Scope, UniDisk behind us, during a slow listing (CH1 /WRREQ J1.10, CH2
  ACK J1.20, CH3 PH3_OUT J3.8; 2 ms/div, 5 V/div, trigger CH1 falling
  1.5 V): a command packet every 1.77 ms, ACK never below 3.0 V (the dips
  are WR crosstalk in the ribbon), PH3_OUT steady at 4.2-4.4 V. The
  UniDisk saw its bus enabled and did not ACK.
  (`docs/captures/m8/2026-10-15_unidisk-behind_wrreq-ack-ph3out_2ms.png`)
- Host line levels (1 V/div): PH0 high 3.5-3.9 V (10k pull-down), WR high
  4.25-4.5 V (100k pull-down). Not the cause.
- +5 at J3.11 (UniDisk feed) with the UniDisk spinning: **4.3 V**. IIe
  slot +5: **5.34 V**. Pulling cards raised the feed to 4.55 V.
- The loss was the thin jumper wire on the +5 path. Replaced with 24 AWG:
  **4.7 V**, and S5,D2 answers at once.

The UniDisk at the end of the chain sits behind our +5 wiring as well as
the Liron cable; every jumper on that path has to be heavy. 4.7 V is still
under the ERS 4.75 V. **[measured]**

## /ENBL pass-through

ENBL_OUT copies host /ENBL under the same rule as PH3 (on after our INIT,
off at reset). With that, the UniDisk behind us takes its INIT and answers
reads. The rule works on the bench. **[measured]**

## Copy through the chain (2026-10-15)

UniDisk behind our board, 24 AWG on +5. Copy II Plus "Copy Disk" from S5,D1
(our board, `/M7TEST`) to S5,D2 (the UniDisk, was `REF800K`): all 1600
blocks, no error. D2 then catalogs as `/M7TEST` (1511 used, 89 free), and
the sentinel boots from the UniDisk's copy: FILE 1-4 OK, sums 55487 /
62070 / 61550 / 61308, ALL 4 FILES OK. Our reads, the UniDisk's writes and
its read-back all went through the pass-through. **[measured]**

## Eject button (2026-10-15)

Plain switch from GP22 (Pico pin 29) to GND (pin 28), no shifter, internal
pull-up; on by default in the firmware. Press and release ejects the disk.
Works.

## Pico on the IIe's +5 (2026-10-15)

Board +5 to Pico VSYS (pin 39) through a small diode (red glass, black band
to VSYS), so USB plugged in later cannot back-feed the IIe rail. USB
unplugged, IIe on: the Pico boots with the IIe, the sentinel boots from our
drive and S5,D2 lists on the chained UniDisk. The whole rig now runs from
the IIe alone. **[measured]**

## Clean-boot check (2026-10-15)

Cold IIe boot, Pico on IIe power, 24 AWG on +5, chain on, UniDisk behind
us. Sentinel boot, catalog of S5,D2, SPCOMPARE on our drive with the disk
write-protected and with no disk. USB plugged in afterwards, with the IIe
