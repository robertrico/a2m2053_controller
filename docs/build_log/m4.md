Mean decode 1179 ns per flux interval (budget 2000 ns: one interval per 2 us at

## Bench findings

### OpenOCD left core 1 debug-halted

After `make flash` / `make reset`, `server on` reported `ERR server did not
start`. Core 1 sat in the boot ROM (PC 0xda, SP 0xf0000000). A cold power cycle
fixed it; `multicore_reset_core1()` before launch did not. Cause: OpenOCD attaches
to both cores (SMP) and leaves core 1 halted under debug. Fix: `set USE_CORE 0`
in the Makefile's OpenOCD config (`4908f0a`); `server on` then works straight
after a reset. The core-1 reset before launch stays (`51f9ff7`, harmless).

### Read data vanished again: disk touching the desk

Mid-session every block came back `0xA7` with only `SOFT_RECAL` set: the decoder
saw no headers at all. The M3-era one-shot `capture` also returned 0 intervals,
and so did the M3 firmware (`e8fc67a`, flashed for an A/B test), so the M4 code
was cleared. Supply voltages at CN104 were normal. Rico found the spinning disk
was touching the desk. After freeing it, flux came back (100000 intervals, 12/12
sectors) and every M4 step passed.

Working theory [guess]: the mechanism mutes RD while spindle speed is out of
tolerance, so drag (or the M3 +5V sag) silences reads instead of corrupting them.
Check next time flux disappears: `tach` and `status 13` (READY). Bench fix: mount
the mechanism so the hub and disk can't touch anything.

## Retest with the mechanism in a bracket

Rico mounted Drive A in a bracket so the hub and disk can't touch anything, then
reran steps 1 to 3 on `main` (`04ce33c`, same firmware as the pass above).

The first `make flash` failed before anything was erased: OpenOCD's flash ROM
calls timed out (`failed to exit flash XIP mode`) and the QSPI flash ID read back
garbled (`0x0316ef`, then `0x16ef00`), at 5 MHz and at 1 MHz SWD. SWD itself
connected (DPIDR 0x4c013477). A power cycle of the Pico (mechanism supply off
first) cleared it, and the next flash verified OK.
